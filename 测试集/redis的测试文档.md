#### Bsave的fork（分支)原理



**fork也可能会导致主线程阻塞，fork是开启一个子进程（并且复制主进程里面的相关数据），需要主线程为fork进程创建页表（大内存进程，页表的页表项很夸张），主要阻塞的原因**

复制**页表共享内存地址**的映射关系，找到对应的存放数据的物理内存

避免主进程写，子进程读的脏数据问题：

- 读就一起读
- 写就额外拷贝一份数据来写，同时主进程的页表指向改变，子进程 **还是读原来的数据**
- 在复制完数据后，关闭子进程，**原来的数据被垃圾回收**，下一次save操作就是指向新的数据

造成的问题：写的频率过高，写的数据量太大会造成副本的内存占有量偏大,可能会造成内存泄漏被强制杀死进程）

- 减少类似缓冲区的数据拷贝

主要的影响因素是：

- 1. 发送了数据读取请求，数据还没准备好，内核准备数据的时间

### 阻塞IO



请求资源一直处于阻塞状态，内核处理请求，直到拿到数据，性能拉完了

对于高并发环境下，CPU都会浪费在**线程调度和切换**上，并且**内存占用大**

### 非阻塞IO



性能也是比较低，虽然只有最后一个获取资源的时候才处于阻塞态，
 但是**一直请求CPU浪费资源处理无效请求**

#### IO多路复用



**引入中间线程，实现解耦合**，顾客不是一个个自己去等待在拿去数据

**分配一个号码牌FD**，线程把请求FD都丢给内核，内核来等待数据，拿到数据以后看一下FD是谁的，就**发送通知**给线程

线程在去拿数据返回给顾客



#### select



对应存储的fd的集合32个元素，一个元素32bit，对应的存储1024bit，这**个不涉及二进制的转换**
 （对应的fd是多少，就存储到第几个bit, 节省空间）

调用函数，把集合发送过去，然后内核就看fd和等待FD的资源准备好了没有

准备好的，**内核把集合里面无关的FD清0**，只保留相关的，
 slelect函数返回有效的**FD的个数**，不返回实际的FD

拷贝内核里面的fd集合回去，**select遍历找到有效的fd**，执行recvfrom操作，循环操作

**缺点**：

- 数组空间有限
- fd数组来回拷贝集合、遍历耗费时间

#### poll



数组没有上限
 对于 fd 对应的事件**设置宏定义**，节点里面保存信息，不**在做不同事件的数组的区分和传递**

#### epoll



句柄epfd是什么

```
为了管理这些被监听的连接，内核需要创建一个专门的“管理者对象”，而 **epfd 就是用来指向这个管理者对象的文件描述符**。内核会创建一个 epoll 实例（内部数据结构是一棵红黑树和一个双向就绪链表），并返回一个代表该实例的句柄，赋值给变量 epfd。
```

callback回调函数，添加到list_head

对于监听fd数组的拷贝，对于select来说，拷贝过一次的fd后续在内核中会消失，还是要再次拷贝到内核

对于epoll来说，不再是拷贝数组，而是**触发函数把要监听的fd添加到红黑树**，之后**长期保存**

对于内核拷贝回去整个fd的数组+就绪fd的数量---->就绪数量，**只有就绪FD的数组，节省了遍历时间**



红黑树允许存储数量上限，性能不影响

#### 事件通知机制



ET在返回就绪fd的数组的同时，会把链表中对应的节点删除

完善数据读取完全的措施：

- **手动添加就绪的fd回链表**，在传递监听的fd的时候，修改操作为mod，只是这样子会涉及多次数组拷贝，性能会比较低
- **一次通知内读完所有数据**，采用非阻塞io+循环的方式读取，直到最后没有数据读取跳出循环

LT缺点

- 多次通知，性能比较低
- 惊群现象，通知到多个线程来处理，产生无效的资源浪费和占用
